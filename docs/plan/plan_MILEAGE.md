# plan_MILEAGE — «пробег не больше 400 000 км, иначе решение review»

План изменений до кода. Правило меняет **решение**, не валидацию: заявки с пробегом
вне [0; 500 000] по-прежнему получают 422 (`vehicle.max_mileage_km`) и до расчёта
решения не доходят.

Основание: `docs/setup/code_map.md` (разделы «Точка вставки правила…», «Что в коде
уже сейчас проверяется про пробег»), границы AC — `docs/spec/README.md:10`
(399999 / 400000 / 400001), разведка @scout от 2026-09-24 (все вызовы `decide()`
и конструкторов `DecisionEngine`, ключи `rules.php`, frontend, db, тесты,
воркдеревья). Числа 400 000 в коде и конфиге сейчас нет.

Семантика правила (предположение до ответа заказчика — см. «Вопросы»):

- пробег <= 400 000 — решение только по LTV;
- пробег > 400 000 — `approve` понижается до `review`; `review` и `reject` не меняются.

Граница правила — 399999 / 400000 / 400001 (в текущем коде отсутствует, вводится этим планом; каждая строка — отдельный случай):

- 399999 — ниже порога: решение по LTV, без понижения
- 400000 — ровно порог («не больше» — включительно): решение по LTV, без понижения
- 400001 — выше порога: `approve` → `review`; `review` и `reject` не меняются
- пустой пробег — до правила не доходит: 422 `ValidationException` на этапе валидации

Новые сигнатуры (единственный код в плане):

```php
public function __construct(array $thresholds, int $reviewAboveMileageKm)
public function decide(float $ltv, int $mileage): string
```

## 4. Риски

1. **Два числа по пробегу**: `vehicle.max_mileage_km` (500000, валидация → 422, `rules.php:23`) и новый `mileage.review_above_km` (400000, решение → review). Если «синхронизировать» `max_mileage_km` до 400000, диапазон 400001–500000 начнёт получать 422 вместо review — фича сломается молча. Оба числа менять только по решению риск-менеджмента (AGENTS.md); план их не меняет.
2. **Слом вызовов при смене сигнатуры**: `decide()` — `AssessmentService.php:33`, `DecisionEngineTest.php:23`; конструктор — `AppFactory.php:37`, `DecisionEngineTest.php:17`, `AssessmentServiceTest.php:27`; других мест нет (проверено scout по репозиторию и трём воркдеревьям, фича нигде не начата). Все правки — одним набором.
3. **approved_limit при понижении**: `review` должен давать лимит 0; логика `AssessmentService.php:39` делает это автоматически, но регрессия здесь — тихая выдача суммы по «перепробежной» заявке; закрывается сквозным тестом (LTV 50 + 400001 → лимит 0).
4. **Граница ровно 400000**: триггер — строго `> 400000`. В проекте уже есть прецедент расхождения комментария с кодом у LTV (`rules.php:39` и `DecisionEngine.php:10` обещают `<=`, код считает `<` в `DecisionEngine.php:32`): докблок нового правила должен формулировать границу однозначно; правка поведения LTV в план не входит.
5. **Пустой пробег неоднороден**: отсутствие поля и `null` дают 422 (`ApplicationValidator.php:43–46`), но пустая строка приводится к 0 и проходит как 0 км; фронтенд шлёт `Number('') = 0`. Существующее поведение, план его не меняет (Вопрос 5).
6. **Сид-данные не покрывают правило**: максимальный seeded пробег 296000 (`db/seed.sql`) — ни одна сид-заявка не задействует порог; работоспособность подтверждается тестами и ручным смоком.
7. **Фронтенд без подсказки**: у поля пробега нет `min`/`max`, форма `novalidate` (`frontend/index.html:16,30–31`) — клиент не предупреждает о пороге; о `review` пользователь узнаёт только после отправки. Осознанно не входит (сервер — единственное место правила).

**Что не входит:** `frontend/`; `db/schema.sql` и `db/seed.sql` (CHECK-ограничений нет, `decisions.decision` уже содержит 'review'); логика и сообщения `ApplicationValidator`; изменение `vehicle.max_mileage_km`; поле «причина review» в ответе API; пересчёт решений уже сохранённых заявок; правка `docs/setup/code_map.md` (в т.ч. найденное scout расхождение на строке 96: `listApplications()` не читает `mileage_km`); `tests/Feature/` (пусты); LOAN-12 (`ltv_by_age`).

## Вопросы, на которые без заказчика не ответить

1. Ровно 400 000 — подтвердить, что не понижает решение (граница «не больше» включительна)? План предполагает: 400000 → решение по LTV.
2. Приоритет факторов: перепробег понижает только `approve → review`, а `review`/`reject` не трогает — подтвердить? Буквальное прочтение «иначе решение review» допускает и «любое решение → review», но это смягчало бы `reject` — план считает это ошибкой риска.
3. 400 000 — утверждённое решение риск-менеджмента или учебное число? (Порог кладётся в `rules.php`, но статус определяет порядок будущих изменений.)
4. Нужен ли в ответе признак причины `review` (LTV против пробега)? Контракт ответа в плане не расширяется.
5. Пустая строка пробега с фронтенда сегодня превращается в 0 км и проходит валидацию (отсутствие поля / `null` → 422). Должно ли пустое поле считаться ошибкой? Правка валидатора в план не входит.
6. Пересчитывать ли решения уже сохранённых заявок при вводе правила? Сейчас решение фиксируется при создании заявки.
7. `vehicle.max_mileage_km` = 500 000 остаётся без изменений? План его не трогает.
